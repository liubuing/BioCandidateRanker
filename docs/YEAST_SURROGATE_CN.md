# 酵母代理：王浆酸场景的毫秒级预测

日期：2026-10-12。承接「先保留泛化性、再聚焦王浆酸」的第三步：把酵母模型纳入代理网格，使王浆酸场景不必每次调用 cobra。

## 一、按模型声明式化（泛化层）

原来两个大肠模型共用一套 8 槽契约与 4 个目标。现在两样都按模型声明：

| 模型 | 特征契约 | 目标集 |
|---|---|---|
| iML1515 / iJO1366 | 培养基 + 融合途径 + 敲除/过表达 + 目标选择子 | growth / nadph / nadh / atp |
| **yeast_metatwin** | 培养基 + **路线** + **POX1 开关** + **目标函数** + 生物量下限 + 目标选择子 | growth / **capacity** / nadph / nadh / atp / **accoa** |

**宽度仍是 8**，所以任何检查点的 `fba_context_dim` 不变；槽位含义按模型声明在 `SCENARIO_FEATURE_IDS_BY_MODEL` 里。目标选择子仍在末槽，新增 `accoa`(4) 与 `capacity`(5) 两个值，不影响既有检查点（它们从不输出这两个值）。

## 二、酵母网格

四个场景轴：**路线 A/B × POX1 开/关 × 目标函数（最大化生长 / 最大化目标容量）× 培养基**。

- 葡萄糖 0.25–3.0（**该模型文件自身的摄取上限是 1.0**，所以网格跨越它而不是用大肠的 6–18）
- 氧 250–1500
- 规模：200 场景 / 1100 行 / **0 剔除 / 0 跨划分泄漏**（划分按场景，四个目标共享）

## 三、训练：一个被我踩到的真实陷阱

**首轮 250 轮训练失败**：6 个目标里 3 个不敌均值基线（atp 0.5×、capacity 0.7×、accoa 1.1×）。诊断信号是 `best_epoch=249/250`——**根本没收敛**。

**900 轮训练（726 轮收敛）后全部达标**：

| 目标 | 测试 RMSE (log10) | 均值基线 | 提升 |
|---|---:|---:|---:|
| 生长 | 0.1059 | 0.6974 | 6.6× |
| NADPH | 0.1342 | 0.5716 | 4.3× |
| NADH | 0.1015 | 0.3740 | 3.7× |
| ATP | 0.2114 | 0.3485 | 1.6× |
| 乙酰-CoA | 0.1752 | 0.6297 | 3.6× |
| **目标容量** | 0.1720 | 0.3930 | 2.3× |
| 池化 | 0.1532 | 0.5329 | 3.5× |

**已固化**：`train_surrogate` 的命令行默认轮次改为 900，并在注释里写明原因；新增测试 `test_trained_surrogates_beat_every_target_baseline_if_present` 会读取本地所有代理的 `metrics.json`，**只要有任一目标不敌基线就失败**——防止将来一次过短的训练被当成可用产物。

### 诚实说明精度差距

酵母代理约 **25–60% 误差**，而大肠代理是 4–10%。原因是酵母场景空间混入了二元制度切换（路线/POX1/目标函数），目标函数随切换而跳变，连续输入的回归器更难拟合。

**用途定位**：酵母代理适合**快速筛选与趋势判断**；要用于定量结论，仍应回到上方的 cobra 运行。这与 `claim_boundary` 的既有口径一致。

## 四、修掉的三个真实缺陷（都是界面/默认值层面的静默错误）

**① 工作台把大肠的培养基默认值带到酵母场景**
葡萄糖输入默认 15、氧默认 20（大肠值）。对酵母代理（训练范围 0.25–3.0）这是**分布外外推**，返回了容量 **12.8953**，而同场景的 FBA 真值是 **0.1667**——差两个数量级，且界面上毫无提示。

**② 由此加了一个分布外守卫（这是本次最有价值的改动）**
`trained_grid_bounds` 声明每个模型的葡萄糖/氧训练范围，`check_query_in_range` 逐轴检查。越界时：数值仍返回，但**在响应与界面上明确标注**"该查询超出训练范围、结果应视为无效、请用 FBA 运行获取答案"。

并修正了界面：**切换 GEM 模型时自动填入该模型声明的培养基默认值**。

**③ 酵母注册表的默认葡萄糖与锚点不一致**
原来声明 10.0（一个通用批次速率），但**该模型文件自身的摄取上限是 1.0**，且外部 10H2DA 锚点 0.274011 用的正是 1.0。也就是说"默认配置"与"文档化的参考案例"给出的是两个不同的答案。现已对齐为 1.0，并写明原因。

## 五、工作台的使用方式

"代谢通量"页签的代理面板现在有三个独立控件（都按所选 GEM 模型刷新）：

1. **代理检查点** —— 只列出该模型的代理（此前会显示另一个模型的检查点，虽然后端按 model_id 推导路径所以结果正确，但界面误导）
2. **代理场景** —— 该模型训练过的场景名。**酵母与大肠的场景词表完全不重叠**，此前共用一个下拉会直接报错
3. **预测目标** —— 只列出该模型声明的目标（酵母多出 `乙酰-CoA` 与 `目标容量`）

## 六、一个遗留的既有松散点（未修改）

`SCENARIOS_BY_NAME` 是两个大肠模型的**并集**，所以理论上可以对 iML1515 请求 iJO1366 的融合场景。这个松散点在本次改动之前就存在（`scenario_input_vector` 层未按模型校验场景归属），我没有扩大范围去改它，但记录在此。

## 七、边界

- 代理是对 **FBA 模拟输出**的蒸馏：训练范围内复现，范围外无效（现已显式标注）
- 酵母代理精度显著低于大肠代理，定量用途应回到 cobra
- 路线容量、辅因子周转仍是模型量，不是实验测量
